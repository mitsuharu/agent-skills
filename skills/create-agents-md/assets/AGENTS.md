## 進め方

- `main` へ直接コミット・pushしない。作業用ブランチを作り、すべてPRで進める。
- 作業を始める前に、現在のブランチ、worktreeの状態、未コミットの変更を確認する。
- 自分の作業と無関係な変更は残す。作者の承認なしにreset・discard・上書きをしない。
- 1 PR = 1目的で、小さく保つ。
- 判断に迷う設計変更や、既存の方針から外れる変更は、マージせず作者（@{{GitHubのユーザー名}}）に確認する。

### ブランチ・コミット・PR

- ブランチ名: `feature/<内容>`, `fix/<内容>`, `docs/<内容>`, `ci/<内容>`, `refactor/<内容>`, `chore/<内容>`
- コミットは目的・機能ごとに分ける。1コミットにテストと実装を含めてよいが、無関係な変更を混ぜない。各コミットが単体で目的を説明できるようにする。
- コミットメッセージはConventional Commits形式（`feat:`, `fix:`, `docs:`, `test:`, `ci:`, `refactor:`, `chore:`）。本文は日本語でよい。
- エージェントがコードの作成・変更またはコミットを行った場合は、コミットメッセージ末尾に空行を挟んで `Co-authored-by: <エージェント名> <メールアドレス>` を必ず付ける。名前は実際に作業したエージェント自身の名前とし、メールアドレスはそのエージェント用のものを使う（例: `Co-authored-by: Codex <noreply@openai.com>`）。マージコミットにも付け、コミット前に付け忘れがないことを確認する。
- PRの説明には「目的」「変更内容」「テスト内容」「要確認事項」を書く。

### マージ

- PRのマージは、作者（@{{GitHubのユーザー名}}）から依頼された場合だけ行う。依頼はその PR（または依頼の中で挙げた PR）に限り、ほかの PR に広げない。
- マージの前に、CIがすべて成功していることと、差分全体を読み直したセルフレビューを済ませる。
- squashではなく、コミット単位の履歴が残るmerge commitでマージする。

### 取り消しにくい操作

- タグ、GitHub Release、パッケージの公開、force push、ブランチの削除など、公開されて取り消しにくい操作は、行う前に作者に確認する。

## コメントとコミットメッセージ

何をどこに書くかを分ける。

| 書く場所 | 伝えること |
| --- | --- |
| コード | How（どう実現しているか）。コード自体で読み取れるように書く |
| テストコード | What（何を保証するか）。テスト名と本文で仕様が分かるように書く |
| コミットメッセージ | Why（なぜこの変更をしたか） |
| コードコメント | Why not（なぜ他の書き方をしなかったか）。自明な処理の説明は書かない |

- 説明文・コメント・ドキュメントは日本語で書く。識別子、パス、コマンドは英語表記のままにする。
- 設定ファイル（CIのワークフローなど）にも、選んだ値と採らなかった選択肢の理由を日本語のコメントで残す。

## GitHub Actions

- サードパーティを含むすべてのアクションは、タグではなくコミットの完全なSHAで固定し、行末にバージョンをコメントで書く。

  ```yaml
  - uses: actions/checkout@<40桁のSHA> # v<バージョン>
  ```

- SHAは推測で書かず、公式リポジトリのリリースタグから確認する（例: `gh api repos/<owner>/<repo>/git/ref/tags/<tag>`、`git ls-remote --tags https://github.com/<owner>/<repo>`。注釈付きタグの場合は指すコミットまでたどる）。
- アクションを更新するときは、SHAとコメントのバージョンを同時に更新する。
- アクションの更新はDependabot（`.github/dependabot.yml` の `github-actions`、月1回）に任せる。新しい依存のエコシステムを追加したら、同じファイルに設定を足す。
- PRを検証するCIは `pull_request` の `types: [opened, synchronize, reopened]` で起動し、`push` トリガーは付けない。必要なら `paths` で対象のファイルを絞る。
- 同じPRで重複して走らないよう、workflowには次の `concurrency` を付ける。

  ```yaml
  concurrency:
    group: ci-${{ github.workflow }}-${{ github.ref }}
    cancel-in-progress: true
  ```

- PRのCIは軽く保つ。成果物の公開やReleaseの作成はPRのCIから行わない。
- キャッシュのキーには、出力の互換性を左右する値（ツールチェーンのバージョン、依存のロックファイル、関連するスクリプトなど）をすべて含める。
- runnerイメージやツールチェーンのバージョンは推測で書かず、[actions/runner-images](https://github.com/actions/runner-images) などの公開情報で確認する。

## 検証

- コミットの前に `git diff --check` を実行する。
- PRを作る前に差分全体を読み直し、不要なファイル、生成物、機密情報が含まれていないことを確かめる。
- 外部のツールやCLIの仕様を書くときは、推測せず公式ドキュメントを確認する。
- 完了を報告するときは、実施した検証と未実施の項目を区別する。

## ドキュメント

- 利用者向けの手順、仕様、対応バージョン、設定項目が変わったら、READMEなどの関連ドキュメントを同じPRで更新する。
- 機能固有の詳細は `docs/` などの別ファイルに置き、このファイルからリンクする。このファイルにはどの作業でも守るルールだけを書く。
- 一時的な作業状態、進行中のPR番号、認証情報、一回限りのデバッグログはこのファイルに書かない。Gitの履歴、PR、issueに残す。

## 完了の定義（各PR共通）

- ビルド・テストが警告やエラーなく通り、CIがすべて成功している
- 追加・変更した振る舞いにテストがある
- 関連するドキュメントが更新されている
- 差分に無関係な変更、生成物、機密情報が含まれていない
